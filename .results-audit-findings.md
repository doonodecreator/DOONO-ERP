# Results Computation Audit — Working Findings

## Confirmed architecture

The codebase contains two overlapping computation paths. The newer path uses `AssessmentStructure`, `ResultComponent`, `AssessmentComputationService`, `ResultProcessingService`, `ResultEntryService`, and `ResultSubmissionService`. The legacy `ResultController` still creates and updates results using `ca_score + exam_score` and hard-coded grade bands. The report-card API reads persisted `ReportCard` rows, while the submission publication service currently updates results and summaries without creating or synchronizing report-card rows.

## Confirmed defects

1. `ResultController::store()` and `update()` bypass configured assessment weights and school-specific grading rules. They calculate raw CA plus exam totals and use hard-coded A–F bands. Its `publish()` method marks a single result published without recomputing summaries, positions, promotion status, or report-card records.

2. `ResultProcessingService::rebuildStudentSummary()` uses a hard-coded pass mark of 40, while the standalone computation service defaults to 50 and promotion uses school configuration. This can produce contradictory passed/failed counts and promotion decisions.

3. `ResultProcessingService::rebuildStudentSummary()` does not scope the `Result` query by school, and its `StudentEnrollment::findOrFail()` lookup is not school-scoped. The downstream summary update can therefore be built from records outside the active tenant if identifiers are ever supplied across contexts.

4. `AssessmentComputationService::computeComponents()` loads assessment structures by global primary key without verifying that the structure belongs to the result’s school. It also silently skips missing structures instead of failing the computation, which can produce incomplete totals.

5. `ResultEntryService::saveStudentResult()` updates or creates a result without including `school_id` in its identity and does not remove stale components when a teacher submits a changed component set. It also allows the saved result’s component set to be incomplete relative to the active assessment structures.

6. Result submission publication toggles result and summary flags but does not create or update the unique `report_cards` row required by `ReportCardController` and the frontend. Therefore results may be published while report-card lists and downloads remain empty.

7. `ReportCardService` contains a second fallback computation with another hard-coded pass mark of 40 and uses an ordinal string for position, while persisted summaries store numeric positions. The report-card payload can therefore disagree with the authoritative processing service.

8. The frontend result-entry page calculates preview grades using fixed percentage bands instead of reading the school grading rules. The backend remains authoritative, but the preview can show a different grade from the saved result.

## Validation still required

The repair must preserve teacher/form-teacher teaching scope, principal approval, publication gating for student/parent portals, and school isolation. Regression coverage should exercise weighted components, grading boundaries, ties, incomplete submissions, report-card synchronization, and a cross-school identifier attempt.

## Repairs implemented

The authoritative component-based pipeline now validates score bounds, school ownership, and active assessment structures; computes weighted totals from the configured maximum marks and percentages; uses deterministic grading-rule lookup; scopes summary and ranking queries by school; uses subject or school-configured pass marks; respects final-term and automatic-promotion settings; and synchronizes report-card rows during submission publication and reopening.

The legacy result controller no longer performs hard-coded CA-plus-exam grading. Its direct write methods return an explicit migration response, while its compatibility publish endpoint delegates to the complete approved submission workflow. Result-entry persistence now includes school identity in the result key, refuses locked or published edits, validates component uniqueness and structure ownership, and deletes stale components when a full score sheet is resubmitted. Result-entry responses include the active school grading rules, and the frontend preview uses those rules instead of fixed bands.

Report-card generation now reuses the authoritative summary pipeline rather than maintaining a second fallback calculator. Report-card resources expose promotion and display metadata, the model can persist all schema fields, and report-card access verifies both report-card and enrollment school ownership. Automatic promotion is now pending unless the school explicitly enables it.

## Validation evidence

All backend PHP files under application, routes, and tests passed syntax checks. Laravel tests passed with five assertions, including weighted-score normalization, invalid-score rejection, and standard competition tie ranking. Result-submission and report-card routes are registered, and the Vite production build passed with only the existing bundle-size warning. Database-backed integration tests remain dependent on the deployment database being available.
