# DOONO De Creator ERP Requirements Implementation Matrix

**Assessment date:** 23 August 2026  
**Basis:** The current Laravel 13 + Sanctum backend, React/Vite frontend, migrations, controllers, services, middleware, routes, shared components, and existing SaaS audit records.  
**Purpose:** Apply the two supplied architecture specifications without replacing working code or pretending that a roadmap item is already complete.

## Status legend

| Code | Meaning |
|---|---|
| **A** | Already implemented and materially wired |
| **B** | Partially implemented; the architecture or workflow exists but has important gaps |
| **C** | Architecture exists but the feature is incomplete or uneven across modules |
| **D** | Not implemented in the current repository |
| **E** | Requires an architectural change rather than a local CRUD addition |
| **F** | Should be deliberately deferred until the trust and daily-dependency foundations are reliable |

## Executive conclusion

DOONO already contains a broad school operating foundation. The safest interpretation of the supplied specifications is **controlled evolution**: preserve the current organization → school → school-user hierarchy, keep `CurrentContextService` as the context authority, keep RBAC in `user_roles`, keep platform and school audit actions separate, and implement new capabilities through shared services and tested workflow boundaries.

The highest-value work is not adding every intelligence or marketplace idea immediately. It is completing the connected workflow chains that make the existing product trustworthy: onboarding → academic structure → staff invitations → student enrollment → fees → payment and receipt → assessment → approval → report card → parent/student visibility → support and audit.

## Cross-cutting implementation contracts

| Contract | Required rule |
|---|---|
| Context | Every school-owned operation resolves organization/school/role through `CurrentContextService`; controllers must not independently guess the current school. |
| Tenant isolation | Backend queries, route model binding, exports, reports, search, files, support tickets, analytics, AI tools, and notifications must enforce school/organization boundaries. |
| Roles | `user_roles.school_id = NULL` is reserved for platform-wide roles; school roles remain attached to their school. Frontend role detection uses the shared helper. |
| Permissions | UI visibility is advisory; backend policy/middleware is authoritative. Scope-sensitive roles must be restricted to assigned classes, subjects, or records where required. |
| Subscriptions | Entitlements use the centralized service; free core, paid features, trials, grants, exemptions, expiry, wildcard plans, and quotas must have one contract. |
| Financial integrity | Payments use immutable references, idempotency, verification, reconciliation, reversals/refunds instead of destructive deletion, and auditable state transitions. |
| AI safety | AI receives only data the user could access normally; generated official content requires human approval; prompts, tools, outputs, and sensitive disclosures are auditable. |
| Automation | Every event-driven action is tenant-aware, permission-aware, retry-safe, idempotent, observable, and auditable. |
| Files | Private files require authorization and short-lived access; file paths must not become an IDOR channel. |
| Support | Support diagnostic context is minimal and authorized; tickets never require passwords, one-time codes, or full payment-card details. |
| UX | Every workflow explains purpose, prerequisites, action, expected outcome, common failure, and recovery path. |

## Recommended no-freeze sequence

The work should continue in parallel, but each stream should have a measurable definition of done.

| Stream | Immediate deliverables |
|---|---|
| Trust | Cross-school negative tests, RBAC tests, protected-file tests, payment replay tests, migration checks, and backup restore drill |
| Daily operations | Finish setup-to-report-card acceptance flow, invitation-to-login flow, fee-to-receipt flow, CBT attempt recovery, and timetable conflict validation |
| Support and onboarding | Add article versioning, FAQs/common mistakes, support notifications, SLA views, and persisted onboarding checklist state |
| Intelligence | First implement explainable analytics and early-warning alerts from real data; label all estimates; defer unrestricted AI assistant behavior |
| Platform | Add structured observability, reconciliation queue, data export, privacy workflows, and safe operational controls |
| Scale | Measure response times, queue latency, database load, and payload sizes before introducing partitioning or regional services |

This matrix is the governing record for the two supplied specifications. Features marked **D**, **E**, or **F** are not silently represented as complete. They should be implemented through separate, inspected, tested changes that preserve the existing DOONO architecture.
